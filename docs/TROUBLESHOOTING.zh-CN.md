# 踩坑与排障

## 1. 导出速度明显偏慢

最大的影响因素通常是本地缓存覆盖率。

如果正文和资源已经在本地，导出主要是本地读取，通常会更快；如果本地缺失，需要回退到服务端补抓，速度和稳定性都会差一些。

建议：

- 先在为知里打开“下载全部笔记”
- 迁移期间尽量保持为知桌面端开启
- 如果正常同步太慢，直接用 `--fetch-missing`

在当前测试版本里，对应的准确设置路径是：

- `设置`
- `同步设置`
- `离线个人笔记` 设为 `全部笔记`
- `离线群组笔记（老笔记）` 设为 `全部笔记`

这两项设置只保证笔记正文的离线下载，不包含附件。

这也是为什么“等待同步完成”很重要。如果在为知本地后台同步还没完成时就启动大批量导出，脚本通常会更频繁地落到服务端补抓路径。为知自己的离线同步即使在正常工作时也可能比较慢，所以这一步需要用户耐心等待。`--fetch-missing` 虽然能在这种情况下继续推进，但失败率通常会高于“本地同步完成后再导出”的情况。

## 2. 协作笔记资源缺失

协作笔记资源可能存在于多个层级：

- IndexedDB
- 浏览器 Cache API
- 编辑器资源缓存
- 为知服务端
- 原始 Electron profile 的磁盘缓存

脚本会按这个顺序逐层尝试。即使笔记在为知 UI 中能看到，也不代表复制出来的 Chromium profile 一定能读到同样的缓存对象。

## 3. 旧 HTML 笔记转换可能有损

有些很老的普通笔记无法稳定通过 HTML 转 Markdown 的转换链。

实际策略是：

- 主路径先走更完整的编辑器转换
- 失败时再走更简单的 fallback
- 极少数笔记仍然需要人工检查

这里的关键边界是：本项目不会把原始 HTML 当成最终导出产物。普通 `export` 也可以在**不改动为知源笔记**的前提下，把旧 HTML 笔记直接导出成 Markdown。

不要假设所有旧 HTML 笔记都能无损转换。

如果你选择 `upgrade-legacy`，那是另一条会写回为知的链路。它会把旧 HTML 笔记转换成 `lite/markdown` 再上传回为知，因此原笔记本身会被改动。

## 4. 网页剪藏笔记的行为不一样

旧网页剪藏的状态并不完全一致。有些可以直接走普通 Markdown 导出链，有些仍然需要 fallback 转换，或者显式执行 `upgrade-legacy`。

较老的 `webnote` 仍可能需要：

- `upgrade-legacy`
- fallback 转换
- 人工 spot check

即使是这类 `webnote`，如果处理成功，最终产物也仍然是 Markdown，而不是原始 HTML 归档。具体是走“导出时直接转换”还是“先升级再导出”，要看笔记本身的状态。

## 5. 升级本身就可能失败

不要假设旧笔记一定能升级成功，无论是在客户端里点升级，还是走导出器侧的写回升级链路。`upgrade-legacy` 更适合作为可选补救路径，而不是一个必然可靠的准备步骤。

## 6. 导出的 Markdown 观感不对

常见原因：

- 整篇正文被最外层 `Plain Text` 代码块包住
- 正文第一行 H1 与文件标题重复
- fallback 转换把网页页眉、版权块之类的杂质一起留下来了

当前脚本已经会自动清理两类常见问题：

- 整篇正文的最外层 `Plain Text` 包裹
- 与笔记标题完全相同的首行 H1

但极少数笔记仍然可能需要单篇手工修补。

## 7. 续跑或重试后的 manifest 看起来不一致

直接执行：

```bash
node scripts/wiz-export.js verify --out ./export --rewrite-manifest
```

这会根据磁盘上的 Markdown 和本地资源重新生成 manifest。对于中断、人工修补后的状态收敛，这是最快的恢复方式。

## 8. 并行重试与 manifest 安全

manifest 只在 `读取当前内容 -> 合并 -> 写回` 这一小段时间内加短锁，真正耗时的转换和下载都在锁外执行。这样可以并行跑多个小范围重试，而不会整轮导出都占着锁。
